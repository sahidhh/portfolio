Sandboxed Coding Agents: free models, checked output

Two personal tools around the Pi coding agent. pi-lean is a backup coding runtime whose tools only run inside a disposable micro-VM. pi-fleet runs small agent jobs (recon, review, small edits, ops reports) on free models, on demand from my laptop or on a schedule on a home server. In both, a job is done only when a script says so.

Role Solo
Stack Pi coding agent, TypeScript extensions, Gondolin micro-VM (QEMU in WSL), PowerShell, Node test runner, systemd
Status In personal use since Sep 2026. Private repos; walkthrough on request.

Why I built it

I use Claude Code daily and sometimes run out of usage mid-task. A lot of what an agent does is low stakes: find where something is defined, review a diff, reformat a doc. I wanted that work on free models, and I wanted a fallback that could still edit code when Claude was unavailable.

The problem

Free models are weaker, and the free router does not say which model served a request. A weak model with shell access on my laptop is a risk, and its "done, tests pass" message is not evidence. Pi itself ships with no sandbox, and its extensions run with full host permissions.

How it works

flowchart LR
  U[me or Claude Code] --> P[Pi\nbuilt-in tools off]
  P <-->|chat + tool calls| M[free model]
  P -->|code_* tools| VM[Gondolin micro-VM]
  VM -->|mount| W[(disposable copy\nof the repo)]
  W -->|export patch| R[patch I review]
  P --> C[check script\npass / fail]
  C --> L[(runs log)]

Sandbox. pi-lean turns off Pi's built-in bash, edit and write tools. The model only sees seven code_* tools (grep, read, edit, write, test, sh, diff) that run inside a Gondolin micro-VM against a disposable copy of the project. Paths are checked, .git is blocked, and output is capped by lines, bytes and seconds. Patch review. The agent never touches the real repo. A script exports its changes as a patch, and I read the diff before applying it. pi-fleet's edit job works the same way in a separate git worktree, gated on at most two files changed and main untouched. Done-checks. Every pi-fleet job has a small check script, and each run appends pass or fail to a log. A failed check is a non-zero exit, whatever the model said.

Decisions that mattered

  • The VM is the boundary. code_sh and code_test run arbitrary code, so I did not try to filter commands. I kept secrets and private code out of the workspace instead.
  • Host-side verification. The eval re-runs tests and diffs the workspace on the host. The model's report is never the score.
  • Short prompt, few tools. A 206-word system prompt replaces Pi's default, and specialist sub-agents stay opt-in. Every registered tool costs schema tokens on every turn.
  • Flags, not a profile. The launcher passes flags to Pi, so global Pi and Claude settings stay untouched and no credentials get copied.

What broke

The first model run reported results it had made up. The cause was mine: wsl.exe re-parsed each command in a host shell, expanding variables and dropping arguments, so tools failed and the model filled the gap. Scripts now go to the guest base64-encoded. The eval checker also had three bugs early on, and the first results table was wrong because of them. Since then I test a scorer on known-good and known-bad runs before I trust it.

Results

12/12eval runs pass on the free router: 6 tasks × 2 runs, including two "target does not exist" refusals
11boundary tests run against the real sandbox
7sandbox tools; Pi's own shell and edit tools are off

Two runs per task on a router with hidden backends is a signal, not proof. Before the prompt rewrite the refusal task failed twice: the model edited an unrelated file and invented a cause.

Not built yet

  • Network allowlist. The VM's outbound network is not blocked yet, which is why nothing private goes in the workspace.
  • Paid-model comparison. The eval takes a --model flag for a cheap coder trial; I have not run it.
  • Specialist agents. Two exist and are opt-in. I have no measured benefit from them, so they stay off by default.
