PDF Diff Tool: same problem as work, the opposite approach

At work I built a config-driven form-comparison pipeline for a client's tax-review platform. On my own time I built a second tool from scratch to test the opposite idea: no per-form config at all — just words, their boxes, and a diff.

Role Solo; the work pipeline was a team build I led on the backend
Stack Python, FastAPI, PyMuPDF, Tesseract, difflib
Work version .NET API + Azure Blob + Python worker + PostgreSQL, JSON locator schema per form
Source

Why I built it

The client project came first. Reviewers on a tax platform compared a new version of an IRS form against last year's by eye — two PDFs, two monitors, a highlighter. We built comparison into the product: a JSON locator schema per form says where each field sits, a Python worker extracts those fields and compares them, a .NET API tracks status and stores the result. It works, and onboarding a new form takes under a day.

But it takes that day. Every new form is a config file someone writes and maintains. I kept wondering what you'd get by skipping the schema entirely and diffing the words themselves — worse precision, maybe, but zero setup. So I built that version at home to find out.

The problem

Tax forms are hostile to naive diffing. Dotted leaders render as rows of the letter m. Underscores and rules become tokens. Some pages are scans with no text layer. A plain text diff of two Schedule M-3s is mostly noise.

Decisions that mattered

  • Diff text, never pixels. The rendered page is only a backdrop. Boxes ride along with words as percentages of the page so they scale with the image.
  • A clean() step before diffing. Drop tokens with no alphanumeric character and runs of 3+ identical single-character tokens. On a 3-page Schedule M-3 that removes ~27% of tokens — all noise. A lone a/b line label survives because only runs are dropped.
  • autojunk=False. difflib's default treats common words as junk and the diff degrades on repetitive form text. Found the hard way.
  • OCR only when needed, and say so. A page with no text layer is rasterized at 300 dpi and read with Tesseract; words under confidence 40 are discarded. Each column header states how its text was obtained and OCR pages get a badge, so reviewers know when to trust it less.
  • Engine has no web dependency. diff_engine.compare(bytes, bytes) is importable on its own and ships a one-line self-check. Same shape as the worker at work, so the two are easy to compare.

Where it landed: the schema-free diff is the right first look — "did anything change on this page?" — and the config-driven pipeline is the right answer for reviewers who need to know which field changed. I'd use the first to decide whether the second is worth running.
