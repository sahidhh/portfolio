Job Discovery Pipeline: only see the postings that match

Scrapes six boards on a schedule, scores each posting against my actual resume in two stages, and sends one Telegram message a run. Dashboard for status tracking and skill-gap analysis.

Role Solo
Stack Next.js 15, TypeScript strict, Supabase, GitHub Actions, OpenRouter, Telegram Bot API
Status In daily use since July 2026
LiveSource

Why I built it

Job boards optimize for time-on-site. I wanted the opposite: zero minutes browsing, and a short list I trust. The first version was a LinkedIn scraper running in Termux on my phone. It worked, but it was mine only, had no memory, and re-showed the same postings.

The problem

Scoring every posting with an LLM is accurate but costs money on hundreds of listings a day, most of which are obviously irrelevant. Sending alerts from a cron job risks duplicates on every retry. And a scraper with no database can't tell "new" from "seen".

How it works

flowchart LR
  subgraph cron [GitHub Actions · 06:00 / 14:00 UTC]
    S[scrape.ts] --> K[keyword score\nfree, always]
    K -->|≥ 0.25| AI[LLM score\nOpenRouter]
    K -->|below| X[skip]
    AI --> N[notify.ts]
  end
  B[(6 boards)] --> S
  S -->|upsert| DB[(Supabase)]
  AI -->|score per job × role| DB
  N -->|check notifications_log| DB
  N -->|digest, Apply buttons| TG[Telegram]
  W[Next.js dashboard] <-->|server actions| DB

Stage 1 is skill overlap between the posting and skills extracted from my uploaded resume PDF — free, runs on everything. Stage 2 calls an LLM with reasoning only for postings above the keyword threshold. Scores persist per (job, role) pair so a re-run never re-scores. A role I type in is expanded once by the LLM into related titles and cached forever; that expansion scopes scraping, scoring and notifications.

Decisions that mattered

  • Two-stage scoring. Keyword gate first, LLM second. Cuts LLM calls to a fraction of listings with no visible loss in the digest.
  • At-most-once notifications. Every send is recorded in notifications_log before delivery is attempted; a retried workflow finds the row and skips. Duplicate pings were the #1 reason I muted the first version.
  • Digest mode by default. One message per run with score bands and inline Apply buttons beats twenty separate pings. Individual mode still exists behind an env flag.
  • No ORM, no state library. Supabase client + server actions. Prisma, Drizzle, Zustand and React Query were considered and rejected; the reasons are written down in the repo's CLAUDE.md.
  • Validate sources as a separate workflow. Board tokens rot. A manual "Validate sources" run tells me which ones broke before the scrape does.
