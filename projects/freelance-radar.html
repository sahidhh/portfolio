Freelance Radar: a CRM with no server, on purpose

Find leads, qualify them, draft outreach, track follow-ups — entirely in the browser. Every status has exactly one next action, so the dashboard always tells you what to do.

Role Solo
Stack React 19, TypeScript, Vite, Tailwind 4, idb, Vitest
Storage IndexedDB only; JSON/CSV export with schema versioning
LiveSource

Why I built it

Freelance CRMs want an account, a subscription, and my prospects' data on their server. For one person with twenty leads that's the wrong trade. I wanted a tool that works offline, costs nothing to run, and can be deleted without a trace.

The problem

Not "build a CRM" — build the smallest thing that answers "what should I do next?" every time it opens, and refuse every feature that needs a server to work.

How it works

flowchart LR
  F[public job feeds\nRemoteOK, Remotive, Arbeitnow, JobDataLake] --> D[Discover]
  D -->|one click| L[Lead]
  L --> Q[qualify: score + reason\noptional PageSpeed audit of their site]
  Q --> O[Outreach\nresearch prompt → draft → mailto]
  O --> FU[follow up]
  FU --> P[Project\nvalue, dates, payments]
  L & Q & O & FU & P --- DB[(IndexedDB\nleads · outreach · projects · activities)]

Pages never touch IndexedDB directly — a db/ layer owns the four stores and export/import. Pure logic (next action, outreach templates, DM budget pacing, feed normalisers) lives in lib/ and is tested against captured real API responses.

Decisions that mattered

  • One next action per status. The pipeline isn't a Kanban for its own sake; each column implies a verb. The dashboard is a list of verbs.
  • Deliberately excluded, in writing: auth, server DB, automated sending, LinkedIn/Upwork automation, scraping, AI agents. External services are used by hand, never as runtime dependencies. The list is in docs/requirements.md so future-me can't quietly add them.
  • Adversarial reviews before each phase. An HN parser and an Instagram lead-sourcing pipeline were designed, reviewed, and cut. The review notes are in the repo alongside the plans that survived.
  • Export with schema versioning. Local-first means the data can be lost with the browser profile. JSON and CSV export carry a version so imports stay valid after the schema changes.
